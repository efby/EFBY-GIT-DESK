# EfbyGitDesk — producto y requisitos

Fecha: 6 de octubre de 2026. Estado: especificación inicial para revisión. Nombre confirmado por el usuario: EfbyGitDesk.

## 1. Propósito y alcance

Crear un cliente de escritorio para **macOS** que permita administrar repositorios Git, comprender sus cambios y ejecutar operaciones cotidianas desde una interfaz visual con terminal inferior. La primera integración remota será **Bitbucket Cloud**. La arquitectura debe seguir Clean Architecture: las reglas del producto y los casos de uso no dependerán de la interfaz, del ejecutable Git ni de la API de Bitbucket.

Las imágenes son referencias visuales: gestor con búsqueda y grupos; vista de trabajo con ramas, historial, comparación lateral y terminal inferior. Sus nombres, cuentas y acciones no constituyen requisitos independientes.

Están confirmados el nombre EfbyGitDesk, macOS, Bitbucket Cloud, Git, ramas, pull/push, copiar SHA, comparación de exactamente dos commits, terminal, apertura/clonación, token/SSH/conexión heredada y Clean Architecture. Son propuestas revisables grupos/favoritos y detalle del MVP. Windows, Linux y Bitbucket Data Center quedan fuera de esta primera versión.

El usuario confirmó que “editar comentario del último push” significa **editar el mensaje del último commit de la rama actual ya publicado**. Se implementará como reescritura acotada de ese commit con las salvaguardas de RF-13.

## 2. Usuarios, resultados y límites

El usuario principal es un desarrollador con varios repositorios que alterna entre interfaz y comandos. Debe encontrar un repositorio, reconocer su estado, sincronizarlo y entender diferencias dentro de la aplicación.

La versión inicial cubrirá repositorios locales con un árbol de trabajo ordinario y remotos Git compatibles con la integración Bitbucket acordada. Clones shallow se detectarán: podrá mostrarse el historial disponible y solicitarse obtener los objetos faltantes. Repositorios bare se usarán para pruebas y remotos; no tendrán editor de cambios ni terminal de trabajo en la interfaz inicial. Worktrees vinculados, sparse checkout y gestión avanzada de submódulos requieren una decisión adicional; las estructuras no soportadas deben identificarse sin modificarlas.

El trabajo local debe funcionar sin conexión a Internet. La autenticación de transporte Git y la autenticación de la API Bitbucket son capacidades separadas: una clave SSH o un credential helper pueden permitir fetch/push sin permitir listar repositorios por API.

La confianza en un repositorio es independiente de la autenticación. Antes de otorgarla, solo se inspeccionan objetos e historial de forma restringida, desactivando diff externo, textconv y fsmonitor; estado del árbol de trabajo, terminal y operaciones de red permanecen bloqueados. La clonación autorizada usa inicialmente `--no-checkout` y hooks vacíos; el checkout requiere confiar en la copia recién creada. La interfaz explica que hooks, filtros y configuración Git pueden ejecutar programas locales.

Quedan fuera del MVP: otros proveedores, IA para explicar commits, revisión y creación de pull requests, pipelines, workspaces en la nube, OAuth, sincronización automática, edición arbitraria del historial, selección de hunks para staging, terminal remoto y actualización automática de la aplicación. Stash, rebase, cherry-pick y merge visual no se incorporan solo porque aparezcan en el mockup.

## 3. Requisitos funcionales

P0 significa necesario para la primera versión. Los criterios Dado/Cuando/Entonces se verifican con el plan de [pruebas y trazabilidad](08-pruebas-y-trazabilidad.md).

| ID / prioridad | Comportamiento y criterio de aceptación |
|---|---|
| **RF-01 / P0** Administrar repositorios | Registrar una carpeta existente, abrir/cerrar pestañas, buscar por nombre/ruta, guardar favoritos, recientes y grupos locales. La ruta canónica evita duplicados. Mostrar y persistir el estado de confianza por repositorio; abrir o heredar credenciales no concede confianza. **Dado** un repositorio registrado, **cuando** se quite de un grupo o del registro, **entonces** sus archivos permanecen intactos. Una carpeta inaccesible conserva el registro y muestra cómo volver a localizarla. |
| **RF-02 / P0** Configurar conexiones | Elegir credenciales de token, SSH o configuración Git existente. Mostrar qué capacidades están disponibles y probar la conexión seleccionada. Guardar secretos mediante el almacén seguro del sistema; importar referencias a agentes/helpers sin copiar claves privadas. **Dado** un clon con SSH operativo, **cuando** se abra, **entonces** se podrá usar su transporte heredado sin exigir token API. Fallos de permisos, host desconocido y credencial expirada se distinguen. |
| **RF-03 / P0** Descubrir y clonar | Listar y buscar repositorios Bitbucket Cloud cuando exista acceso API, o aceptar una URL de clonación compatible sin catálogo. Seleccionar destino y mostrar progreso/cancelación. Clonar sin checkout ni hooks y solicitar confianza antes de materializar archivos. **Dado** un destino no vacío, **cuando** se intente clonar allí, **entonces** la operación se rechaza sin sobrescribirlo. Un fallo deja una carpeta parcial identificable; su limpieza requiere acción explícita. |
| **RF-04 / P0** Consultar estado | En repositorios confiables, mostrar rama, HEAD, upstream, modificaciones, staging y conflictos. Antes de confiar, restringirse a lectura segura de objetos/historial. Indicar cuándo ahead/behind usa información remota almacenada y cuándo se verificó por fetch. **Dado** un repositorio confiable sin Internet, **cuando** se abra, **entonces** historial, estado y diferencias locales siguen disponibles; las acciones remotas muestran el fallo sin bloquear la navegación. |
| **RF-05 / P0** Gestionar ramas | Listar ramas locales/remotas, crear desde una referencia y cambiar de rama. Borrar ramas locales únicamente tras comprobar que no están activas ni utilizadas por otro worktree; advertir commits no integrados. **Dado** cambios que impedirían checkout, **cuando** se cambie de rama, **entonces** se conserva el trabajo y se explica el bloqueo. No se aplica stash ni descarte automático. |
| **RF-06 / P0** Obtener referencias | Fetch del remoto elegido con progreso y actualización posterior del estado. La eliminación de referencias obsoletas exige una opción explícita. **Dado** un fetch satisfactorio, **cuando** termine, **entonces** se actualizan las referencias y ahead/behind sin cambiar la rama actual ni el árbol de trabajo. |
| **RF-07 / P0** Incorporar cambios | Pull usa fast-forward como comportamiento inicial. Si falta upstream, solicita configurarlo; si hay divergencia, informa y requiere una resolución explícita mediante herramientas acordadas o terminal. **Dado** un historial divergente, **cuando** se solicite pull, **entonces** no se inicia un rebase, merge, stash o descarte automáticamente. |
| **RF-08 / P0** Publicar cambios | Push muestra rama local, remoto y rama destino. Permite establecer upstream y devuelve los rechazos del servidor. **Dado** un remoto que avanzó, **cuando** se solicite push normal, **entonces** se conserva el estado local y se informa el rechazo. No existe force push genérico en el MVP; la excepción acotada es RF-13. |
| **RF-09 / P0** Preparar y crear commits | Stage/unstage de archivos completos y commit con mensaje. El resumen separa cambios preparados y pendientes. Respetar hooks y configuración de firma; mostrar su resultado sin alterar la política del repositorio. **Dado** archivos sin preparar, **cuando** se confirme el commit, **entonces** solo se incluyen los preparados. En una rama sin commits, la operación inicial funciona; índice vacío o mensaje vacío se rechazan. |
| **RF-10 / P0** Explorar historial y copiar SHA | Mostrar grafo, mensaje, autor, fecha y referencias con carga paginada y lista virtualizada. Buscar sin presentar una página parcial como historial completo. Copiar el identificador completo, aunque se muestre abreviado. **Dado** un commit seleccionado, **cuando** se copie su SHA, **entonces** el portapapeles recibe el identificador real completo. |
| **RF-11 / P0** Comparar exactamente dos commits | Activar comparación únicamente con dos commits diferentes. Etiquetar origen A y destino B y permitir intercambiarlos; el tercer intento de selección conserva el par y explica el límite. Comparar árboles A→B, también en commits de merge o sin relación de ancestro; no sustituir A por merge-base. **Dado** dos commits, **cuando** se comparen, **entonces** se enumeran todas las rutas cambiadas con su estado y diferencias disponibles. Cero/uno seleccionados no activan comparación. |
| **RF-12 / P0** Ver diferencias locales y de archivos | Separar worktree frente a índice e índice frente a HEAD. Mostrar diff unificado o lado a lado, árbol o lista de rutas, altas/bajas/renombrados, modos y cambios de enlace simbólico. Binarios, punteros LFS y referencias de submódulos tienen resumen específico. **Dado** un archivo demasiado grande para el visor, **cuando** se abra, **entonces** permanece en el inventario y aparece el límite aplicado; no se omite silenciosamente. |
| **RF-13 / P0** Editar el mensaje de HEAD | Editar solo el commit HEAD de una rama, manteniendo su árbol y autor, y mostrar que cambiará el SHA. Bloquear índice con cambios preparados, operaciones Git incompletas y estado que no pueda verificarse. Respetar hooks y firmar de nuevo según configuración; nunca reutilizar una firma anterior. **Dado** un mensaje local editado, **cuando** termine, **entonces** existe una referencia de recuperación del SHA previo y el contenido del commit es idéntico. Para publicarlo: fetch previo, comprobar que HEAD anterior era el tip remoto de la rama destino, mostrar ese destino y solicitar confirmación específica de reescritura. Usar lease con el OID remoto esperado; si cambia, falta permiso o la política del servidor lo prohíbe, detenerse conservando la recuperación local. |
| **RF-14 / P0** Usar terminal inferior | Terminal interactivo PTY por repositorio con directorio correcto, entrada, salida, redimensionado, Ctrl+C, pestañas y cierre. Shell y comandos se ejecutan con los permisos del usuario. **Dado** un commit o checkout hecho por comandos, **cuando** cambie el repositorio o vuelva el foco, **entonces** la interfaz invalida y recarga el estado. La terminal permite operaciones externas; no se promete aislamiento absoluto frente a ellas. |
| **RF-15 / P0** Controlar operaciones | Serializar las escrituras iniciadas por la aplicación por repositorio, permitir lecturas compatibles y distinguir progreso, fallo y cancelación. Revalidar HEAD/índice/referencias antes de aplicar una escritura. **Dado** otro proceso que cambia el repositorio o mantiene un lock, **cuando** una acción choque con él, **entonces** se informa sin borrar locks ni repetir acciones destructivas. Cancelar no implica revertir efectos ya ejecutados. |
| **RF-16 / P0** Configurar la experiencia | Persistir distribución de paneles, visibilidad y altura de terminal, repositorios y preferencias locales. Navegación por teclado, foco visible y nombres accesibles para iconos conforme a macOS. **Dado** un reinicio normal, **cuando** se abra la aplicación, **entonces** recupera la distribución sin restaurar procesos terminales como si siguieran vivos. Idioma definitivo por acordar antes del diseño final. |

## 4. Requisitos no funcionales

Estos umbrales son objetivos iniciales; se medirán con equipos y fixtures documentados y se validarán antes del lanzamiento.

| ID | Requisito verificable |
|---|---|
| **RNF-01** Arquitectura | Dominio y aplicación no importan UI, SDK del proveedor ni APIs específicas del sistema. Paquetes Swift separan capas; UI en MainActor y actores coordinan operaciones. Adaptadores intercambiables y contratos verificados; no se presupone IPC ni proceso de renderer. |
| **RNF-02** Seguridad | Secretos en Keychain y fuera de configuración/logs; argumentos estructurados y validación de rutas entre capas. No concatenar entradas en comandos de shell para acciones Git de la interfaz. Aplicar el estado de confianza también en los casos de uso, no solo en controles visuales. Las huellas SSH nuevas o cambiadas requieren una decisión visible. |
| **RNF-03** Integridad | No perder archivos por acciones de registro, checkout bloqueado, clone fallido o cancelación. Recuperación para edición de mensaje; errores con estado observable y sin promesas falsas de rollback. |
| **RNF-04** Respuesta | En un repositorio de referencia de 100.000 commits, primera página del historial en ≤2 s con caché cálida y ≤5 s fría; percentil 95 de interacción de selección/scroll ≤100 ms. Diff pesado, Git y red fuera del hilo UI; progreso visible en acciones prolongadas. |
| **RNF-05** Accesibilidad | Flujos P0 operables con teclado, sin depender solo del color para estados; contraste y VoiceOver revisados en macOS. |
| **RNF-06** Compatibilidad | macOS y Bitbucket Cloud; declarar versiones mínimas de macOS/Git y arquitecturas de CPU soportadas. Git del sistema y adaptadores macOS para terminal/credenciales; detectar capacidades ausentes antes de ofrecer acciones dependientes. |
| **RNF-07** Diagnóstico | Eventos y errores estructurados con correlación de operación y redacción de URL con credenciales, tokens, rutas sensibles y contenido terminal. Exportación de diagnóstico revisable por el usuario; telemetría externa fuera del MVP. |
| **RNF-08** Mantenibilidad | Tests de dominio/casos de uso, integración con Git real y contratos de adaptadores. Instalador verificable, documentación de decisiones y migraciones compatibles de preferencias. |

## 5. Definición de primera versión aceptable

Una sesión debe completar registro/clonación, checkout, preparación, commit, fetch/pull/push, copia de SHA, comparación de dos commits, edición de mensaje y refresco tras comandos. Los flujos locales funcionarán sin API ni red.

El lanzamiento requiere cumplir los criterios P0 y el plan QA para macOS y Bitbucket Cloud. Debe quedar documentado cualquier límite de historial, visor o estructura Git; ningún límite de renderizado puede convertirse en omisión del inventario de cambios.
